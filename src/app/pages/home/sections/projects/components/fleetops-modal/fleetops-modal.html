TRANSACTIONAL OUTBOX PATTERN

Dual-Write Hazard vs Atômico com Outbox

Em sistemas distribuídos, publicar diretamente no broker durante a requisição HTTP gera risco de perda irreversível de mensagens se houver crash da aplicação ou falha de rede logo após o commit do banco. O Transactional Outbox unifica o estado e o evento sob a mesma transação ACID do PostgreSQL.

FleetOpsDbContext.SaveChangesAsync (Interceptação ChangeTracker) C# 14 / EF Core 10 
public override async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    var aggregatesWithEvents = ChangeTracker.Entries<AggregateRoot>()
        .Where(e => e.Entity.DomainEvents.Count > 0)
        .Select(e => e.Entity)
        .ToList();

    if (aggregatesWithEvents.Count > 0)
    {
        var outboxMessages = aggregatesWithEvents
            .SelectMany(a => a.DomainEvents)
            .Select(OutboxMessage.FromDomainEvent)
            .ToList();

        await OutboxMessages.AddRangeAsync(outboxMessages, cancellationToken);
    }

    var result = await base.SaveChangesAsync(cancellationToken);

    foreach (var aggregate in aggregatesWithEvents)
    {
        aggregate.ClearDomainEvents();
    }

    return result;
}
HIGH-CONCURRENCY WORKERS

Concorrência Multi-Réplica via FOR UPDATE SKIP LOCKED

Em clusters Kubernetes com múltiplos pods da API executando em paralelo, múltiplos processos de Outbox realizam polling na tabela outbox_messages. O FleetOps resolve contenção de lock com bloqueio pessimista a nível de linha: workers paralelos selecionam lotes disjuntos imediatamente sem aguardar linhas bloqueadas por réplicas concorrentes.

SQL Polling Concorrente sem Bloqueio PostgreSQL 18 
SELECT * FROM outbox_messages
WHERE processed_on_utc IS NULL AND attempts < @maxAttempts
ORDER BY occurred_on_utc
LIMIT @batchSize
FOR UPDATE SKIP LOCKED;
⚡

Particionamento Dinâmico de Carga

Réplica 1 bloqueia mensagens 1 a 20. A Réplica 2 ignora imediatamente as linhas travadas e consome as mensagens 21 a 40 sem espera.

🛡️

Zero Espera de Lock na Seleção

Elimina contenção de polling (lock_wait = 0ms), impedindo deadlocks entre pods paralelos sob alta vazão.

🔄

Isolamento de Falha Automático

Em crash abrupto de uma réplica, a transação aborta e o PostgreSQL libera os locks instantaneamente para o worker seguinte.

OPTIMISTIC CONCURRENCY

Concorrência Otimista com PostgreSQL xmin (MVCC)

Todas as entidades principais utilizam a coluna de sistema oculta do PostgreSQL xmin mapeada como token de concorrência. Se duas conexões lerem o veículo na versão X e tentarem alterar atributos concorrentemente, o PostgreSQL atualiza para X+1 no primeiro commit; o segundo falha com DbUpdateConcurrencyException, sendo mapeado para HTTP 409 Conflict ProblemDetails.

OIDC RESOURCE SERVER

Autenticação OAuth 2.0 / OpenID Connect via Keycloak

O FleetOps opera estritamente como um Resource Server, delegando credenciais e emissão para o Identity Provider Keycloak. Tokens JWT são assinados assimetricamente com RS256 e validados dinamicamente via JWKS dinâmico com cache in-memory e resiliência offline contra quedas do IdP.

Assinatura Assimétrica RS256

Keycloak assina com chave privada RSA-2048; a API consome a chave pública via descoberta OIDC e certificados JWKS (/certs) com rotação transparente sem reinicialização.

Backchannel vs Emissor Canônico

No Docker, valida o emissor público canônico (http://localhost:8080/realms/fleetops) enquanto consome JWKS pela rede interna (http://keycloak:8080/...), prevenindo hairpinning DNS.

RBAC com Extração Estrita

Roles de cliente extraídas estritamente de resource_access.fleetops-api.roles mapeadas para ClaimTypes.Role, prevenindo escalonamento de privilégios.
